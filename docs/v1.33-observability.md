# Production observability

Milestone 19 adds privacy-safe request correlation, structured logs, operational
metrics, error-reporting hooks, and stronger readiness checks without introducing
an external monitoring dependency.

## Request correlation

Every response includes `X-Request-ID`. TuneForge accepts an inbound ID only when
it is 8–64 characters from a strict letters/numbers/dot/underscore/hyphen
alphabet; otherwise it generates a random 128-bit ID. The ID is available to
application logs through a context variable and is returned on safe unexpected
error responses as well as normal responses.

Request events record only:

- method;
- normalized route template, never raw path IDs;
- status code/class;
- duration; and
- request ID.

Query strings, questions, form fields, passwords, cookies, session tokens, API
keys, uploaded filenames/content, evidence text, and provider payloads are not
request-log or metric dimensions.

## Structured logging

Configure:

```text
TUNEFORGE_LOG_LEVEL=INFO
TUNEFORGE_LOG_FORMAT=json
```

Production defaults to JSON; development defaults to readable text. JSON events
contain UTC timestamp, level, logger, stable event name, request ID, message, and
bounded event fields. Existing tracebacks remain server-side and safe HTTP 500
responses never disclose exception messages.

Stable events cover request completion, auth-boundary denial, invalid login,
rate-limit rejection, trusted-web completion, extraction failure, provider
fallback, citation-validation failure, and readiness failure.

## Operational metrics

Administrators can read process-local metrics at:

```text
GET /api/v1/operations/metrics
```

The endpoint is outside the anonymous allowlist and requires the administrator
role. It reports process start time, uptime, bounded counters, and aggregate
request timing (count, average, maximum). Labels are stable, bounded identifiers.

Coverage includes:

- HTTP count/status and route-template latency;
- unhandled request exceptions;
- authentication failures and boundary denials;
- rate-limit events by surface;
- manual and evidence extraction outcomes;
- trusted-web outcomes and page-fetch failures;
- provider validation/fallback outcomes;
- citation-validation failures;
- answer and recommendation refusals; and
- database/readiness checks and failures.

Metrics are operational signals, not the append-only product audit trail. They
reset on process restart and contain no user content. A future monitoring agent
may scrape the protected endpoint or adapt the registry to Prometheus/OpenTelemetry
without changing domain workflows.

## Health and readiness

`GET /api/v1/health` remains a cheap liveness probe with no database dependency.

`GET /api/v1/ready` now verifies:

- database connectivity;
- Alembic revision;
- SQLite `PRAGMA quick_check`;
- zero foreign-key violations;
- actual temporary-file creation in uploads storage;
- actual temporary-file creation in evidence storage; and
- actual temporary-file creation in backup storage.

The probes remove temporary files immediately and expose only booleans plus the
schema revision. A failed required check returns HTTP 503 and emits a bounded
operational event.

## Error reporting integration

`set_error_reporter()` registers an optional process hook for Sentry or another
deployment-specific reporter. The default is no-op. The hook receives the
exception plus bounded request ID/method/path context and is isolated so reporter
failure cannot break the application. No vendor SDK, DSN, or secret is required
or committed by this milestone.

Like rate limiting, the built-in registry is intentionally process-local for the
current single-process SQLite profile. Multi-instance production should export
events and metrics to shared infrastructure rather than treating per-process
counters as global totals.
