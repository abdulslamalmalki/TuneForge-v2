# BIOS version awareness

TuneForge can attach reviewer-approved firmware-version boundaries to Guidance Claims. The
model remains citation-first: version scope is metadata on a reviewed claim, never a value
inferred from a manual title, a user-entered string, or an LLM.

## Scope model

Each BIOS scope belongs to one Guidance Claim and one explicit context:

- an exact normalized motherboard model; or
- a normalized motherboard vendor.

A scope records one or more documented lifecycle markers (`introduced_in`, `changed_in`,
`deprecated_in`) and may additionally define either an exact version or a valid range. Every
scope requires reviewer-authored version notes and an evidence basis. Scope changes are
captured in the claim's append-only event snapshots and remain editable only while the claim
is a draft.

Firmware identifiers default to `opaque`. Opaque identifiers can be matched exactly but are
never ordered. A reviewer must explicitly choose `integer_numeric` or `dotted_numeric` before
TuneForge accepts a range. Both domain validation and database constraints reject an opaque
range. Reviewed hardware targets and BIOS contexts are also checked for contradictory board
or vendor identities.

## Retrieval behavior

Users may optionally enter the BIOS version exactly as firmware displays it in My System.
TuneForge does not persist that input as a hardware profile and does not normalize it into a
different vendor's version scheme.

Citation-first facts expose one of five BIOS match states:

- `unscoped`: no reviewed BIOS boundary exists;
- `version_not_provided`: a relevant boundary exists, but the user supplied no version;
- `matched`: an exact or explicitly comparable range matched;
- `not_applicable`: the reviewed context or comparable version did not match; or
- `unknown`: the scope is lifecycle information only, or the user value cannot be compared
  under the reviewed scheme.

The state is explanatory in this milestone. Claims are preserved side by side across firmware
releases; a newer claim never overwrites an older claim. Conflict detection and final
applicability filtering are separate retrieval responsibilities.

## Review syntax

The reviewer page accepts one scope per line. For example:

```text
motherboard_model:asrock-x870e-taichi-white | exact=3.20 | mode=opaque | notes=Behavior documented for this release | basis=Official board documentation reviewed
vendor:asus | from=1801 | until=1904 | mode=integer_numeric | notes=Documented release interval | basis=Official release history reviewed
```

Supported keys are `exact`, `from`, `until`, `introduced`, `changed`, `deprecated`, `mode`,
`notes`, and `basis`.

## Migration and recovery

Migration `0025` adds `guidance_claim_bios_scopes` without modifying existing claims. The
production migration started with zero scope rows by design: no historical claim was
auto-rescoped.

The migration was validated on an isolated restore through upgrade, downgrade, and re-upgrade,
followed by SQLite integrity and foreign-key checks. The post-migration recovery checkpoint is:

```text
data/backups/tuneforge-v1.33.0-bios-version-awareness.zip
SHA-256: 144269f08856523a283f9b6e211219c1216d3d85db7fa3bdf089e06d60e97ee1
Database revision: 0025
```

An independent restore verified revision `0025`, SQLite integrity `ok`, zero foreign-key
violations, revoked authentication sessions, and zero public-knowledge audit failures.
