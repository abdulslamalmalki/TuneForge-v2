# Safe recommendation knowledge foundation

TuneForge now has a recommendation knowledge model that is deliberately separate from
factual Guidance Claims. A fact such as “this setting controls a limit” cannot silently become
an action such as “set this limit to 200.” Recommendation claims have their own evidence,
scope, lifecycle, review queue, and append-only history.

This milestone does **not** enable generic “best BIOS settings,” personalized tuning plans, or
LLM-generated values. Public Ask TuneForge continues to return
`recommendation_status: not_available` even if a recommendation claim has been approved. A
future exact applicability and safety resolver must be completed before recommendations can
be presented publicly.

## Structured model

Each recommendation belongs to one active Canonical Setting and records:

- a normalized action: enable, disable, set an exact value, set a documented range, leave on
  Auto, avoid, or informational;
- an exact value or range only when the selected action requires it—free-form values cannot
  attach to other actions;
- one supported use case: gaming, productivity, efficiency, quiet operation, overclocking,
  undervolting, memory tuning, or stability troubleshooting;
- risk, prerequisites, confidence, and conflict-assessment state;
- one or more approved Evidence Passages or trusted approved Source Settings;
- at least one normalized, evidence-backed hardware target; and
- optional reviewed motherboard/vendor BIOS-version boundaries.

Source Setting evidence must already map to the selected Canonical Setting. BIOS ranges retain
the existing TuneForge rule: opaque firmware labels can match exactly but cannot be ordered.
Every hardware and firmware boundary stores its reviewer-authored evidence basis.

## Review and publication gates

New records always begin as drafts. Draft edits replace structured links transactionally and
append before/after snapshots to `recommendation_claim_events`. Approved and rejected records
are immutable.

Approval fails closed unless all of the following are true:

1. evidence remains approved and trusted;
2. normalized hardware applicability is present;
3. confidence is `high` or `very_high`;
4. conflict state is `none` or `resolved`; and
5. a human reviewer records a note and named audit actor.

The protected `/recommendation-claims` workspace exposes draft, approved, and rejected queues,
complete citations, scope, structured values, prerequisites, reviewer controls, and event
history. The admin dashboard shows both reviewed recommendation count and pending review work.
The versioned protected API mirrors the same domain workflow under
`/api/v1/recommendation-claims`.

## Schema and migration safety

Migration `0027` adds six isolated tables:

- `recommendation_claims`;
- `recommendation_claim_evidence`;
- `recommendation_claim_source_settings`;
- `recommendation_claim_applicability_targets`;
- `recommendation_claim_bios_scopes`; and
- `recommendation_claim_events`.

Existing Guidance Claims and public read models are unchanged. No historical factual claim is
converted into a recommendation and the production migration intentionally creates zero
recommendation rows.

The schema uses database checks for action/value coherence, supported use cases, risk,
confidence, conflict state, lifecycle status, one-target hardware identity, BIOS context,
firmware comparison mode, and reviewer evidence text limits. Hardware target columns are not
speculatively indexed: current access is by the `(claim_id, ordinal)` primary key, and future
exact-resolution indexes will be added only from measured query plans.

An isolated `0026 → 0027 → 0026 → 0027` cycle is part of the integration suite and verifies
schema revision, SQLite integrity, foreign keys, and complete table reversal.

## Explicitly deferred

The following remain unavailable by design:

- generic or model-memory-based tuning advice;
- recommendation inference from factual Guidance Claims;
- value/range generation;
- fallback from an exact system to a broader board, chipset, platform, or vendor;
- conflict reconciliation by an LLM;
- public recommendation retrieval or formatting; and
- automated approval.

The next dependency is an improved user hardware profile followed by an exact applicability,
BIOS-version, conflict, and safety resolver. Until that chain can prove a reliable match,
TuneForge must refuse to recommend.
