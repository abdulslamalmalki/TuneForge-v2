# Security audit and hardening

Milestone 17 performs an adversarial review of TuneForge's authentication,
authorization, browser, upload, local-storage, outbound-network, provider, URL,
SQL, template, error, and dependency boundaries.

## Concrete findings fixed

### External work on GET requests

The public Answer page could invoke a paid model provider and live official-web
research from a GET request. Trusted-web API research was also a GET even though
it writes an append-only research run. Crawlers, link previews, browser
prefetching, or cross-site navigation could therefore trigger network work and
cost without an explicit same-origin action.

Read-only Answer links now perform deterministic local retrieval only. Search,
optional model presentation, and live research use explicit POST forms protected
by the existing Origin/custom-header policy. The trusted-web API is now POST.

### Path-only public authorization

The anonymous route policy used public path prefixes without considering the
HTTP method. A future write route under `/library/` could have inherited public
access accidentally. Public access is now an explicit method-and-path policy:
only known POST actions are anonymous, while Library and API prefixes are GET
only.

### DNS validation race in live research

Official-page research previously checked that DNS returned only public IPs and
then allowed the HTTP library to resolve the hostname again. That separation
left a DNS rebinding/check-use race.

The transport now:

1. validates the exact HTTPS hostname, credentials, and port;
2. resolves it once and rejects empty, private, loopback, link-local, metadata,
   reserved, or mixed public/private answers;
3. connects to a selected address from that validated set;
4. performs normal TLS certificate and hostname verification using the official
   hostname;
5. bounds time and response bytes and requests identity encoding; and
6. repeats URL, DNS, address pinning, TLS, domain/host, and redirect validation
   for every hop.

The configured live-search service uses the same pinned transport and cannot
redirect away from its configured host. A bounded real request to AMD's official
site completed with a validated 64-character SHA-256 snapshot.

### Stored-path trust

Database filenames were generated by the server, but path helpers did not
independently enforce that invariant. Manual and evidence paths now accept only
their exact generated filename grammar, staged uploads must remain inside the
upload directory, and staged deletion finalization validates its target.
Traversal, alternate extensions, absolute paths, and invalid IDs fail closed.

### Browser URL confusion and open redirects

Local return paths now reject backslashes, controls, network paths, and absolute
URLs. Official provenance and evidence URLs reject malformed ports,
non-standard ports, credentials, controls, backslashes, and domain lookalikes.
Search service configuration accepts only structurally valid public HTTPS
endpoints on the standard port.

### Upload resource bounds

The existing 100 MiB streaming limit, server-generated filenames, hashing,
deduplication, content parsing, and cleanup remain. Intake now also requires a
PDF signature within the first 1,024 bytes and applies a configurable page-count
limit (`TUNEFORGE_MAX_PDF_PAGES`, default 5,000) before acceptance.

### Browser response policy

Production responses now include HSTS. All responses receive a same-origin
opener policy in addition to the existing CSP, frame denial, MIME protection,
referrer policy, permissions policy, and trusted-host validation. Authentication,
Answer, and upload surfaces are explicitly non-cacheable.

## Controls reviewed and retained

- PBKDF2-HMAC-SHA256 passwords use unique salts and 600,000 iterations.
- Unknown users use a dummy password hash and login errors do not enumerate
  accounts.
- Session cookies are opaque, server-side, HttpOnly, SameSite Strict, and Secure
  is mandatory in production; only token hashes are stored.
- Password resets, account disablement, logout, and role enforcement retain
  their existing session revocation and append-only audit behavior.
- Jinja autoescaping remains enabled; the only search snippet markup escapes
  source text before inserting fixed `<mark>` tags.
- Application SQL uses ORM expressions or bound parameters. No application
  command execution, unsafe deserialization, or raw user-formatted SQL was
  found.
- Unexpected errors retain server-side tracebacks but return generic public/API
  messages.
- Optional provider responses remain byte-for-byte claim/citation validated and
  bounded; provider errors and response bodies are not disclosed.

## Dependency review

`pip check` passes. `pip-audit` initially found one advisory in the local
development environment's transitive `cryptography 49.0.0`; that environment
was updated to `50.0.0`, after which no known installed-package vulnerabilities
were reported. `knowledge-builder` itself is local and therefore correctly
reported as unavailable on PyPI. Reproducible production dependency resolution
is handled in production preparation rather than pretending the mutable local
virtual environment is a lock file.

## Validation

Focused adversarial coverage exercises method-aware authorization, same-origin
external execution, DNS private/mixed answers, pinned connections, redirect
escape, URL confusion, open redirects, path traversal, upload bounds, production
headers, official-domain enforcement, and deterministic provider fallback.

Rate limiting and structured security-event metrics are intentionally separate
roadmap milestones and follow this audit. PDF parsing remains an in-process,
bounded operation; a future high-volume hostile deployment should isolate
parsing in a resource-limited worker process or container as an additional
defense layer.
