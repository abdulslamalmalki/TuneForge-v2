# TuneForge v1.33 complete canonical backlog classification

## Outcome

Milestone 3 investigated and classified the complete population of 2,812
approved source settings that do not currently have a canonical mapping. This
does not claim that all settings are equivalent across vendors. It converts an
opaque backlog into an explicit evidence and research worklist.

The applied run produced:

- 2,812 current approved-unmapped settings
- 2,812 persistent assessments
- 0 missing assessments
- 935 conflicts with competing candidates
- 1,044 insufficient-evidence records with no defensible existing identity
- 803 records needing research
- 29 records needing human review
- 1 strong candidate (`PSS Support` → `pss-support`, 91.83%)
- 0 automatic mappings
- 0 changes to the 99.5% automatic mapping threshold

The idempotency rerun created or updated zero records and reported all 2,812 as
unchanged.

## Classification is not truth

`canonical_backlog_assessments` stores the current investigation state. An
assessment never creates a `setting_canonical_mappings` record and never creates
a canonical identity. Mapping remains exclusively controlled by the existing
reviewer workflow and deterministic automatic path with all hard gates intact.

System-assessed and human-confirmed states are explicit. A deterministic rerun
does not overwrite a human-confirmed conclusion. Every initial assessment,
reassessment, human conclusion, and later mapped resolution is append-audited.

Supported reviewer outcomes are:

- verified exact mapping
- strong candidate
- likely equivalent
- partial equivalence
- related but not equivalent
- vendor-specific
- needs human review
- needs research
- insufficient evidence
- conflict

The engine assigns only outcomes defensible from internal evidence. Nuanced
semantic conclusions remain human decisions.

## Evidence packet

Every assessment preserves:

- source setting and reviewed description
- vendor, manual, official URL, and page
- candidate canonical identity when present
- deterministic confidence and every score signal
- support setting IDs
- reviewed BIOS menu path when available
- competing-candidate and missing-gate reasons
- new-identity proposal details when relevant
- engine and threshold versions

## Reviewer workflow

The protected `/canonicalization/assessments` interface provides outcome,
vendor, and review-state filters; complete evidence detail; previous/next
navigation; and explicit reviewer conclusions. The existing canonicalization
screen links to this worklist and remains the only mapping action surface.

Run or verify the classifier with:

```text
python -m tools.classify_canonical_backlog \
  --output data/reports/canonical-backlog-classification.json
```

Use `--dry-run` to roll back assessment mutations after producing a report.
