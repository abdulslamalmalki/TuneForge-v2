# Grounded model providers

Milestone 12 connects TuneForge's existing provider-neutral presentation
contract without changing the source of truth. Retrieval, canonical resolution,
hardware/BIOS applicability, conflict handling, citations, and refusals remain
deterministic application responsibilities. A model can only reproduce a
reviewed presentation packet.

## Trust boundary

The runtime flow is:

```text
Question
  -> deterministic TuneForge retrieval
  -> reviewed evidence statements + citation IDs
  -> optional provider
  -> strict JSON parser
  -> exact claim/citation/scope validation
  -> validated presentation OR deterministic fallback
```

The provider receives:

- exact approved claim text;
- claim type, claim ID, and applicability scope;
- public citation metadata and passage IDs;
- reviewed hardware and BIOS scope metadata attached to those claims;
- the exact required output draft and required notices.

It does not receive the user's query, system profile, vendor aliases, search
suggestions, referral pointers, raw evidence passages, review workflow state, or
live trusted-web results. Refused envelopes do not call a provider.

The system instruction prohibits pretrained BIOS facts, browsing, inferred
values/defaults/compatibility/safety/recommendations, omission, merging,
reordering, and conflict reconciliation. The validator independently enforces
the rule: any changed claim text, claim identity, citation set/order, scope
notice, recommendation notice, malformed JSON, provider identity mismatch, or
provider failure causes the model output to be discarded.

## Adapters

| Provider ID | API | Credential | Notes |
|---|---|---|---|
| `openai` | Responses API | required | Strict JSON Schema response format; storage disabled per request. |
| `anthropic` | Messages API | required | Top-level system instruction and JSON-only contract. |
| `gemini` | `generateContent` | required | JSON MIME type and response schema. |
| `openai_compatible` | `/chat/completions` | optional | Operator-configured endpoint; supports keyless loopback models. |

The HTTP transport is synchronous because the public route is a synchronous
FastAPI handler. It disables redirects, bounds time and response bytes, requires
JSON, rejects duplicate JSON keys, normalizes upstream failures, and never
returns raw upstream bodies to users. Plain HTTP is permitted only for
`localhost`, `127.0.0.1`, or `::1`; remote compatible endpoints require HTTPS.

The adapter payload shapes follow the providers' primary documentation:
[OpenAI Responses and model guidance](https://developers.openai.com/api/docs/guides/latest-model),
[Anthropic Messages API](https://platform.claude.com/docs/en/api/messages/create),
and [Gemini generateContent](https://ai.google.dev/api/generate-content).
Model IDs are configuration, not application constants, so updating a model
does not alter TuneForge's knowledge or validation architecture.

## Configuration

The default is provider-free:

```dotenv
TUNEFORGE_LLM_PROVIDER=
TUNEFORGE_LLM_MODEL=
TUNEFORGE_LLM_API_KEY=
TUNEFORGE_LLM_BASE_URL=
TUNEFORGE_LLM_TIMEOUT_SECONDS=20
TUNEFORGE_LLM_MAX_RESPONSE_BYTES=262144
```

For an official provider, set `TUNEFORGE_LLM_PROVIDER`, an explicit model ID,
and the API key through the deployment secret manager. Do not put keys in the
repository or a committed `.env` file.

For a keyless loopback OpenAI-compatible server:

```dotenv
TUNEFORGE_LLM_PROVIDER=openai_compatible
TUNEFORGE_LLM_MODEL=<installed-model-id>
TUNEFORGE_LLM_BASE_URL=http://127.0.0.1:11434/v1
TUNEFORGE_LLM_API_KEY=
```

Startup validation rejects unknown providers, missing model IDs, missing keys
for official providers, unsafe plain-HTTP remote endpoints, credential-bearing
URLs, query/fragment-bearing URLs, and unreasonable timeout/response limits.

## Failure behavior

TuneForge never depends on provider availability. Authentication failures, rate
limits, timeouts, transport errors, non-JSON responses, oversized responses,
invalid provider shapes, and output-validation failures all use the existing
deterministic reviewed answer. The public page reports only whether optional AI
formatting passed or whether deterministic fallback was used; it never exposes
credentials or raw provider errors.

## Validation status

All four adapters are exercised with mocked HTTP transports. Tests verify
request shape, credential placement, response normalization, size limits,
unsafe URL rejection, error normalization, runtime selection, exact provider
acceptance, unsupported-fact rejection, and deterministic public fallback.

No live API request was made for this milestone because no provider credentials
were available. This is an external validation blocker only; the deterministic
product path and mocked production integration are complete.
