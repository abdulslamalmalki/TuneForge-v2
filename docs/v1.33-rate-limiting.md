# Production rate limiting

Milestone 18 adds configurable sliding-window limits at TuneForge's existing
authentication and same-origin boundary. Development and tests remain unlimited
by default; production startup refuses to run unless rate limiting is enabled.

## Protected surfaces

The policy targets work with meaningful abuse or cost potential:

| Surface | Default policy |
|---|---:|
| Login and first-run setup | 10 requests / 300 seconds |
| Ask TuneForge POST, including optional provider work | 30 / 60 seconds |
| Trusted-web research API | 10 / 60 seconds |
| Public manual submission | 5 / 3,600 seconds |
| Curator manual, batch, and evidence upload | 60 / 3,600 seconds |
| Non-empty Answer/Library/search reads | 120 / 60 seconds |
| Other protected admin/API mutations | 120 / 60 seconds |

Static assets, ordinary Library browsing, details, health checks, and other
inexpensive read-only pages are not limited.

Configure each policy as `requests/window_seconds`:

```text
TUNEFORGE_RATE_LIMIT_ENABLED=1
TUNEFORGE_RATE_LIMIT_LOGIN=10/300
TUNEFORGE_RATE_LIMIT_ASK=30/60
TUNEFORGE_RATE_LIMIT_RESEARCH=10/60
TUNEFORGE_RATE_LIMIT_PUBLIC_UPLOAD=5/3600
TUNEFORGE_RATE_LIMIT_CURATOR_UPLOAD=60/3600
TUNEFORGE_RATE_LIMIT_SEARCH=120/60
TUNEFORGE_RATE_LIMIT_ADMIN_MUTATION=120/60
```

Malformed, zero, negative, or extreme policies fail startup validation.

## Identity and privacy

Authenticated requests are keyed by the internal numeric user ID. Anonymous
requests are keyed by the ASGI client address. TuneForge does not store query
text, passwords, cookies, session tokens, API keys, uploaded content, or form
fields in limiter state.

The limiter is thread-safe, uses monotonic time, removes expired entries, and
caps distinct in-memory buckets. When capacity is exhausted, new identities use
a shared per-surface overflow bucket instead of allowing unbounded memory growth.

## Responses

Successful limited requests and HTTP 429 responses include:

```text
RateLimit-Limit
RateLimit-Remaining
RateLimit-Reset
```

Rejected requests also include `Retry-After`. APIs return the normal safe JSON
error shape; browser surfaces return a generic plain-text message. Limits run
after same-origin and authentication policy, so rejected cross-origin or
unauthenticated internal requests do not consume protected-user capacity.

## Deployment boundary

The limiter is deliberately process-local. TuneForge's current SQLite deployment
profile is a single application process, making that behavior deterministic and
avoiding a new availability dependency. A future multi-instance deployment must
move shared enforcement to a trusted reverse proxy or a purpose-built shared
store. Client identity must come from the ASGI server or a correctly configured
trusted proxy; do not trust arbitrary forwarded-address headers.

An edge/WAF limit remains useful for volumetric denial-of-service protection.
The application limiter is the product-specific second layer, not a replacement
for network-level controls.
